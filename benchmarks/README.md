# 1.0.0 conversion comparison

The public tables in `readme.txt` come from [1.0.0.json](1.0.0.json). They measure four full-size files through the release candidate's production conversion code, with quality 80 for both JPEG and PNG. The benchmark found and led to a fix for WordPress resetting the requested quality during output-format conversion. Only results after that fix are published.

The test used an Apple M1 Pro with 32 GiB RAM, macOS 26.6.2, PHP 8.4.23, WordPress 7.1.1, and headless Chrome 153.0.8010.52 in a dedicated profile. The JSON records the installed GD and ImageMagick versions. The browser used the shipped WebAssembly module; PHP used the plugin's normal conversion handler, with each server editor selected by a filter in the disposable test site.

Each file/backend combination had one warm-up and five measured conversions. Plugin-owned output was removed before each run. Times were measured with `performance.now()` from the production conversion call to its saved response. Browser measurements include prepare, source download, worker startup, decode/encode, validation, upload, and saving. Server measurements include the AJAX request, decoding, encoding, validation, metadata, and saving. Both ran over loopback on the same computer. The initial page/codec download, queue waiting, fixture preparation, and output inspection are outside the timer. Every saved result was checked for its encoder label, dimensions, valid WebP format, bytes, and SHA-256; repeated outputs were deterministic within each backend.

The median of the five measured times is published. Sizes use decimal KB (1,000 bytes). Savings are `(1 - outputBytes / sourceBytes) * 100`. GD and Imagick produced the same sizes for these inputs, so the public size table combines them; the timing table lists them separately. Larger-output skipping was disabled to permit measurement of every output, although all four outputs happened to be smaller. The normal plugin default still skips copies that are not smaller.

## Inputs

- Large JPEG: 3000 × 1348 landscape photograph, JPEG quality 90, 1,077,531 bytes.
- Small JPEG: 600 × 270 version of the same photograph, JPEG quality 90, 51,382 bytes.
- Large PNG: the same 3000 × 1348 RGB raster, PNG compression level 6, 6,105,941 bytes.
- Small PNG: 600 × 400 transparent artwork generated by `scripts/prepare-screenshot-site.php`, 2,627 bytes.

The photo is [Fronalpstock big.jpg by Hannes Röst](https://commons.wikimedia.org/wiki/File:Fronalpstock_big.jpg), licensed under [CC BY-SA 3.0](https://creativecommons.org/licenses/by-sa/3.0/). The downloaded 3840-pixel preview was resampled with PHP GD to the two dimensions above. The JSON includes its download URL and hashes of the actual test inputs. Images and temporary benchmark endpoints are not included in the plugin package.

Four examples cannot establish a typical compression ratio. A photo stored as PNG is very different from an already compact transparent graphic. Matching quality numbers do not establish equal visual quality across encoders; no perceptual-quality metric was measured. Real hosting, CPU contention, device speed, latency, and upload bandwidth change the timings. Generated thumbnail sizes add work. Safari was tested for functionality separately and is not part of this speed comparison.

The WordPress.org parser and WordPress plugin-details window remove HTML table tags. The public readme therefore uses compact, aligned text tables in supported preformatted blocks; the rendered result is checked in the actual WordPress 7.1.1 details window.
